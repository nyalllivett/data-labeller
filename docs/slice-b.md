## Decisions

Names are required trimmed NFC strings. Reject ASCII/C1 control characters before trimming; preserve internal whitespace, case, emoji and legitimate Unicode joiners. No invented length/count cap. Duplicate display names are allowed: identity is the stable UUID, never the name. Renames retain IDs; archive/restore retains the label and is idempotent. Archived labels are excluded from future capture selection. Historical naming policy: slice C must snapshot each recording's used label names alongside IDs; later rename/archive must not rewrite those snapshots. No recording exists in this slice.

Each project is a small aggregate with a monotonically increasing revision. SQLite stores committed aggregates and submitted operations. Save freezes an operation ID, expected revision and desired aggregate. Staging persists that intent; an exclusive transaction checks revision and writes the aggregate and completion marker together. Repeated taps/retries reuse the operation ID. An operation ID with different content is rejected. Ambiguous write failure is reconciled by reading that ID; conflict preserves pending intent and current committed data. A submitted change cannot survive process death before staging succeeds; unsaved typing is not promised as a persisted draft. No database is silently reset on corruption or unsupported schema.

Native storage preparation must succeed before SQLite opens: iOS persistent Application Support/DataLabeller directory with verified backup exclusion; Android noBackupFilesDir/data-labeller. No fallback to cache or backup-eligible defaults. A tiny local Expo module owns those primitives. Controlled native doubles test JS coordination. Native policy unit sources/targets now exercise the shared helpers against filesystem doubles, but have not executed here; actual native compilation, filesystem guarantees and backup/device-transfer behavior remain unverified. Native unit execution and later iOS-first device checks are separate gates.

The pinned React Native exception manager is wrapped before application import/registration. Its delegate receives only a new fixed-code error with an empty stack, preserving fatal/nonfatal status. The original exception is never inspected or forwarded. This bounds caught/uncaught paths routed through that manager; it does not sanitize arbitrary console calls, native-originated reports, earlier startup errors or development tooling. Expected repository failures are normalized independently. Installation failure blocks the data-bearing root rather than reverting to raw reporting.

Pragmatic scope: the owner clarified during this review follow-up that safeguards must have credible triggers and impact. The discard bug is reachable through the existing UI, so it is fixed with early ID guards and disabled controls, without new queues or a state framework. The metadata journal remains: app interruption and ambiguous SQLite outcomes are realistic; retaining submitted intent, atomic revision updates and same-ID recovery protects submitted changes and prevents duplicate/conflicting saves. The existing serial adapter/busy guard handles ordinary repeated taps and asynchronous operations. No extra persistence layer or hardening is added. Native helpers isolate only the filesystem operations already required; Swift relies on FileManager's creation failure for a file at the destination instead of adding a duplicate directory-type check. Android retains its existing directory verification because `mkdirs()` can fail without throwing. Backup-exclusion readback and fixed error normalization address the explicit local-only/privacy requirements.

## Implementation and evidence

- Domain: `src/projects/project.ts`. Projects/labels retain UUID identity, canonical names and creation order; pure changes return a new revision, with no-op rename/archive preserving the current object. Persisted JSON is validated and reconstructed from known fields. The pending operation is cloned and frozen before asynchronous work, including labels.
- Persistence: `ProjectRepository`, `SqliteProjectRepository` and `nativeRepository`. Parameterized SQL binds all private values. Schema 1 contains committed project aggregates plus pending/completed operations. Exclusive transaction callbacks use the supplied transaction object. Startup rejects newer/invalid schemas before writing; migrations are transactional. WAL and FULL synchronous mode are requested, but actual power-loss/fsync guarantees are not claimed. Queue failures do not poison later requests.
- Coordinator: `ProjectStore` keeps last committed state while saving, serializes UI actions, retains same-ID retry intent, and survives render-boundary remount. Relaunch applies staged operations using stored payloads/revisions; conflicts remain visible for explicit retry or confirmed discard. A completed older operation returns the latest aggregate rather than overwriting newer work. Discard deletes only an incomplete operation, never a committed project/completed outcome. An unconfirmed discard remains a discard across in-process retry/remount. Actions for a different pending request are rejected before state mutation or repository access until the discard outcome is confirmed. Regression tests retain A's intent across failures while B is pending, reject B's discard/retry, then verify B becomes actionable after A completes. A process death before discard commits can leave the original staged save available for relaunch reconciliation; discard is not acknowledged before commit/read confirmation.
- UI: `ProjectWorkspace`, `ProjectList`, `ProjectDetails`, shared `NameEditor` and `RecoveryPanel`. Forms retain failed input, guard busy/conflicting actions, distinguish load failure from an empty workspace, and confirm discarding submitted intent. Other requests' retry/discard/confirmation controls are disabled during an unconfirmed discard, while the matching Retry discard remains available; tests include a confirmation already opened before the failure. Async editor completion does not update an unmounted editor. All forms/screens use controlled component tests; scrolling/keyboard/native accessibility acceptance remains deferred.
- Diagnostics: fixed operation-state and normalized failure-code events. No error contents, project/label names, URIs or metadata JSON enter app logs. This deliberately sacrifices raw native error detail; `unavailable` covers unknown native/storage failures rather than inventing unsupported error classifications.

Verified installed dependencies: `expo-sqlite@57.0.4` and `expo-crypto@57.0.3`, selected by installed Expo 57's table and actually installed. `randomUUID()` supplies identifiers; unit tests inject deterministic IDs. No ORM, router, backend, libSQL connection, auth or telemetry uploader is configured. [Expo SQLite](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/) documents exclusive transactions and parameter binding. Installed SQLite [iOS source](https://github.com/expo/expo/blob/50ac74f1ab5682c8e32b24da6e5e97dd4dbbb80f/packages/expo-sqlite/ios/SQLiteModule.swift) defaults to Documents/SQLite and lacks a backup-exclusion open option; this job supplies a prepared directory explicitly. Inspected SQLite iOS/Android path handlers accept file URIs.

`modules/private-storage` is a small local [Expo module](https://docs.expo.dev/modules/get-started/), discovered by both platform autolinking commands. iOS creates Application Support/DataLabeller, sets and reads back [`isExcludedFromBackup`](https://developer.apple.com/documentation/foundation/urlresourcevalues/isexcludedfrombackup), and normalizes native failure to fixed text. Android creates a directory under `noBackupFilesDir`, checks it is a directory, and also normalizes failure. [Android's backup guidance](https://developer.android.com/identity/data/autobackup) distinguishes no-backup directories from `allowBackup=false` alone, which can have manufacturer-specific device-transfer limits. Native sources are included in Git: generated-root ignore patterns were anchored so they do not hide the local module. SQLite WAL/SHM/journal files reside within the same prepared directory. Directory preparation/exclusion is rechecked each initialization; no memory/cache/default-directory fallback exists.

Privacy adapter evidence is version-pinned to React Native `0.86.3`: [renderer error handlers](https://github.com/facebook/react-native/blob/v0.86.3/packages/react-native/src/private/renderer/errorhandling/ErrorHandlers.js) delegate caught/uncaught errors to the manager property; [ExceptionsManager](https://github.com/facebook/react-native/blob/v0.86.3/packages/react-native/Libraries/Core/ExceptionsManager.js) forwards raw errors to console independently of native payload decoration. Thus a payload decorator or ErrorUtils-only shim is insufficient. The isolated private import is declared narrowly, shape-checked, installed idempotently and verified writable. Tests use hostile incoming getters and controlled delegates, preserving fatal/nonfatal forwarding and fixed failure propagation. Captured third-party references can bypass the wrapper. A future RN upgrade must recheck this private ABI; these unit tests do not prove native exception reporting on a device.

## Native policy unit targets

Four filesystem closures isolate Application Support lookup, idempotent creation and exclusion set/read. The podspec explicitly includes only the module and policy sources, keeping Package.swift/tests/build output out of production. Seven XCTest methods specify new/existing/repeated preparation, every thrown primitive failure, a file at the destination, missing/false exclusion, operation order, and fixed NSError domain/code/message with no original metadata/underlying error. This is a macOS host target, not an iOS application acceptance test.

Android's `PrivateStorageDirectory.kt` has no Android/Expo imports. It invokes the nullable context/root provider and URI converter inside the error-normalization boundary, using a three-method filesystem interface. Creation is followed by directory verification. Seven [local JVM test methods](https://developer.android.com/training/testing/local-tests) use controlled doubles for new/existing/repeated preparation, missing context, provider/filesystem/URI exceptions, creation failure and a file at the destination. Failures assert fixed text and no original cause/suppressed errors; later steps must not run. No actual filesystem, Android framework or instrumentation test is used by these tests.

The module's local Gradle unit target declares `junit:junit:4.13.2`, matching the installed Expo Crypto/Modules Core unit dependency; it adds no runtime dependency, Robolectric or mock-default Android behavior. Android autolinking resolves project name `private-storage`; the documented task is `:private-storage:testDebugUnitTest`.
