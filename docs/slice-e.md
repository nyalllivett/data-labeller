## Proposed minimal contract

1. Authoritative, human-readable UTF-8 `annotations.json`, with `format: "data-labeller"`, integer `schemaVersion: 1`, `timeUnit: "milliseconds"`, `timeBasis: "recorded-media"`, `intervalConvention: "half-open"` and `unlabelled: "not-negative"`. "Canonical" means authoritative annotations, not cryptographic canonicalization or reproducible ZIP bytes. No CSV in E: nested provenance/untimed failures and reviewed/original values need the JSON; optional tabular projections can be agreed later.
2. One unencrypted ZIP for a selected saved recording or the project's saved recordings. Its root contains `annotations.json` and the existing `<recording UUID>.mov/.mp4` filenames. IDs, never user names, establish media linkage and avoid duplicate-name/path problems. No transformations, transcoding or timestamps derived from JS wall time.
3. Include export scope and the committed current project snapshot. Each packaged recording contains an actual relative `videoFile` string, its immutable `originalCapture` snapshot and its committed `effective` reviewed document/revision. Effective revision `0` is exactly the original interval list with ordinal IDs; positive revisions are saved overlays. An empty effective array remains deliberate deletion of all intervals. IDs are original capture-interval ordinals scoped to that recording, not current list indices. Preserve historical labels, overlaps, zero-length bounds, gaps, event order (including equal times), timing source/unknown lag and untimed failures. No normalization, snapping or invented caps. Only saved revisions export; no hidden in-memory review edits. Pending drafts acquire no invented duration/finalized intervals.
4. Project packages include an explicit pending-recording annotation inventory, marked `videoIncluded: false`, alongside all saved recordings. Pending video cannot be represented as safely saved, is never promoted by export, and is excluded visibly in the screen and manifest. Interrupted clips and untimed failures remain visible warnings and original evidence. A selected-recording package includes only that selected saved recording; other project recordings/pending work are outside its scope. Disable package creation when no saved video exists. A failed media/annotation read blocks the package rather than silently skipping a saved recording or falling back to capture intervals.
5. Validate schema/scope, identity linkage, known filename mapping, original captured data and effective interval bounds through pure owned rules. After native ZIP completion, check the exact expected file inventory and uncompressed byte sizes, plus a nonempty output. Reject duplicate/unexpected paths, directories, encrypted entries and size mismatches. Measure the JSON file's UTF-8 bytes, not JavaScript string length. This checks packaging metadata, not native CRC/decoded media/durability acceptance; do not claim those from doubles.

Proposed concrete v1 fields/types and cross-reference rules, so consumers need no app to understand validation:

| Field | Type and rule |
| --- | --- |
| Header fields above | Exact fixed literals; schema version is `1` |
| `scope` | `{ kind: "recording", recordingId: UUID }` or `{ kind: "project" }`; selected scope contains exactly its recording and no pending inventory |
| `project` | `{ id: UUID, name: string, revision: positive safe integer, labels: [{ id: UUID, name: string, archived: boolean }] }`; names are nonempty trimmed NFC strings without control characters; duplicate names allowed, IDs unique |
| `recordings` | Array of `{ videoFile: string, originalCapture: object, effective: object }`; recording IDs unique, belong to `project.id`, and filenames exactly `<originalCapture.id>.<extension>` |
| `originalCapture` common fields | `{ id, projectId: UUID, projectName: string, facing: "front" or "back", extension: "mov" or "mp4", labels: [{id: UUID, name: string}], events: [{labelId: UUID, mediaMs: number, source: string}], annotationFailures: [{labelId: UUID, afterEvent: nonnegative safe integer, reason: string}], termination: "stopped" or "interrupted" }`; captured names are historical snapshots |
| Saved media fields | `durationMs: positive finite number`, `byteSize: positive safe integer`, `intervals: [{labelId, startMs, endMs}]`, `timing: "native-reported-position"`, `lagBoundMs: null`; original intervals derive from ordered toggle events plus duration |
| Events/failures | Known captured label IDs; event times positive, finite, nondecreasing and within saved duration; source is `avcapture-recorded-duration` or `camerax-recording-stats`. Failure `afterEvent` is an original event-list boundary from `0` to event count; reason is `clock-unavailable` or `invalid-timing`. Failure does not invent a timestamp |
| `effective` | `{ recordingId: UUID, revision: nonnegative safe integer, intervals: [{id: nonnegative safe integer, labelId: UUID, startMs: number, endMs: number}] }`; ID matches capture, interval IDs unique and less than original interval count, labels belong to captured snapshot, finite `0 <= start <= end <= duration`; overlaps/zero duration allowed. Revision `0` exactly matches original intervals/ordinals; no missing-versus-empty ambiguity |
| `pendingRecordings` | Array of `{ videoIncluded: false, originalCapture: draft }`; unique IDs disjoint from saved IDs, matching project; draft has only common capture fields above with termination also allowed to be `null`, no duration/media bytes/finalized intervals/timing assertion invented |

UUIDs use the app's lowercase standard UUID string form. Every effective/original time is milliseconds on the recorded media basis. These fields do not assert physical tap/frame alignment. Project exports include all saved and pending rows from the frozen library snapshot; source-load failure is not an exclusion. Final public contract documentation and decoder units will accompany the reviewed encoder.

## Installed packaging/share evidence and proposed boundary

Installed exact `react-native-zip-archive 9.5.3` and `expo-sharing 57.0.22` with npm. The latter matches the installed Expo SDK table and [official SDK 57 sharing docs](https://docs.expo.dev/versions/v57.0.0/sdk/sharing/). Registry git heads are respectively `69d1fc8cc6aeca4fe560b1ee3b33a0da49b39e6d` and `9349d1457178dd9cccb8bdd3aed47473c49134e1`. Native compilation remains unavailable/unverified; installation and peer/API evidence do not establish native acceptance.

- ZIP [types/JS](https://github.com/mockingbot/react-native-zip-archive/blob/69d1fc8cc6aeca4fe560b1ee3b33a0da49b39e6d/index.js) accept file arrays and a native output path. The [iOS array implementation](https://github.com/mockingbot/react-native-zip-archive/blob/69d1fc8cc6aeca4fe560b1ee3b33a0da49b39e6d/ios/RNZipArchive.mm) uses SSZipArchive file-path writes with each file's basename; [Android](https://github.com/mockingbot/react-native-zip-archive/blob/69d1fc8cc6aeca4fe560b1ee3b33a0da49b39e6d/android/src/main/java/com/rnziparchive/RNZipArchiveModule.java) adds native Files through zip4j. Proposed input is the known committed media paths plus the small JSON file, with no duplicate video staging and no video bytes crossing JS.
- The ZIP package targets React Native >=0.70/React >=18, includes New Architecture codegen, and documents development-build support. Native dependencies are zip4j `2.11.5` and SSZipArchive `~>2.5.5`; source/runtime compatibility and their actual resolution/linking remain native checks. The config plugin is a no-op; add the documented registration entry without enabling services.
- Use the library's no-compression option for already-encoded video. ZIP creation remains native/background. Do not subscribe to path-bearing progress events or log native messages; owned diagnostics use fixed codes only.
- Its JS AbortSignal helper races an early rejection against native completion. Do **not** use that early rejection as a cleanup/retry boundary. Request native `cancel()` only for an active archive, retain the actual zip promise, and wait for it to settle before discarding incomplete output or starting another archive. Serialize preparation through inventory inspection because the native cancellation flag is global. Native source checks cancellation between files, so show "Cancel requested; finishing the current file" without a timeout or latency promise. Local cancellation intent wins even if the last file finishes and native ZIP resolves successfully. Metadata preparation also checks the request between awaits. A failed cancel request can still discard the output after work settles; no source changes occur.
- A narrow package adapter owns a UUID-named app-cache workspace, JSON writing, direct path-array ZIP creation, entry inspection and final-name promotion. Existing read-only saved-media resolution is reused. All deletes target only that workspace; sources and databases are never moved, deleted or modified. Cleanup failure remains explicit and must resolve before retrying a failed/cancelled attempt. No recovery journal or scan of original media is needed for a reproducible cache artifact.
- Completed ZIPs remain in app cache for Share/retry and may be evicted by the OS. Do not delete a successfully prepared/shared ZIP immediately on share-sheet return or Back: [Android sharing](https://github.com/expo/expo/blob/9349d1457178dd9cccb8bdd3aed47473c49134e1/packages/expo-sharing/android/src/main/java/expo/modules/sharing/SharingModule.kt) resolves on chooser activity return and grants a FileProvider URI; this does not prove the receiver has finished reading. Cache loss triggers re-preparation from intact sources. No arbitrary retention duration/storage quota is introduced.
- The [iOS SDK](https://github.com/expo/expo/blob/9349d1457178dd9cccb8bdd3aed47473c49134e1/packages/expo-sharing/ios/SharingModule.swift) resolves on dismissal regardless of completion/cancellation. The [JS API](https://github.com/expo/expo/blob/9349d1457178dd9cccb8bdd3aed47473c49134e1/packages/expo-sharing/src/Sharing.ts) returns void. A separate explicit Share action checks availability and opens the local ZIP via OS UI. Report "Share sheet closed; delivery is not confirmed", never "Exported/shared successfully". Android sets its pending promise before chooser launch and does not clear it in catch; launch failure can block same-session retries. Keep the ZIP and offer full-app-reopen guidance for persistent failure, without a new native recovery framework or universal Retry guarantee. No receiving/import extension is enabled.

## Proposed implementation and verification

Small pure schema/validator functions, an ExportStore outside the render subtree, a narrow package adapter and separate sharing adapter. Load the saved/pending library, let the user choose one recording or project scope, prepare a frozen committed snapshot, then offer Share separately. Active preparation/cancellation/sharing guards conflicting actions/navigation. Errors and retries retain scope/intent; packages never silently omit failed saved inputs. No general job framework, uploader, CSV converter or custom native ZIP format implementation.

Existing Astra architecture agent supplied read-only advice on this working proposal; the concrete fields, ordinal/revision semantics, inventory/UTF-8 checks, cancellation winner and Android launch-failure caveat above incorporate it. That advice does not replace the parent's requested schema/packaging check or final independent acceptance review.

Meaningful units will cover serialization/linkage/provenance, schema/data validation, selected/project scope and pending/incomplete inventories, annotation/media read failures, preparation/cancellation/cleanup sequencing, low-storage/ZIP failures, retry/repeated actions, cache eviction, share availability/failure/return uncertainty and components. Required full units, types, zero-warning lint, reproducible installation, both bundles and applicable generation/config/autolinking checks precede final handoff. Native/device acceptance remains separate, iOS first later; no integration suite.
